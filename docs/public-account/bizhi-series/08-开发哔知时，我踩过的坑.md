# 开发哔知时，我踩过的坑

**文 / 逸峰AI**

哔知看起来是一条很顺的链路：导入收藏夹，抓字幕，生成洞察，写成笔记，再沉淀到知识库。但真正开发起来，我踩过的坑比想象中多得多，因为它不是一个单纯的前端工具，而是把 B 站、Tauri、本地 Python、ASR、AI API、Markdown 和文件系统都串在了一起。

第一个坑是批量处理。最开始我也想让系统一口气处理大量收藏，后来发现这既不符合使用场景，也容易把应用拖垮。后台并发太高会卡，AI 调用会产生费用，字幕和转写失败时还会堆出一堆难以理解的状态。最后我把方向改成单条触发：用户选择真正需要的视频，再对这条视频抓字幕、生成洞察和笔记。

第二个坑是字幕质量。原生字幕不一定存在，本地 ASR 也可能误识别，标题和字幕还可能对不上。早期我用标题关键词做强校验，结果一些正常视频因为口播没重复标题而被拦截。后来我把校验改成分级：明确错配和文本过短才阻止，低置信则允许继续生成，但提醒用户抽查。这个改动很重要，因为工具不能为了追求“看起来安全”而打断真实工作流。

第三个坑是界面主次。刚开始我把太多状态、标签、按钮都塞进页面，结果信息密度高到影响阅读。后来才意识到，哔知的核心不是展示所有流程，而是让用户知道下一步该做什么：这条视频有没有字幕，有没有洞察，有没有笔记，能不能继续处理。其他信息应该折叠到处理中心、帮助与反馈或右侧详情里。

第四个坑是本地依赖。ffmpeg、yt-dlp、FunASR、模型缓存、Python 虚拟环境，每个环节都可能因为用户机器不同而出问题。对开发者来说这是日志，对普通用户来说就是“软件坏了”。所以 Doctor 诊断不是锦上添花，而是必须做的基础能力，它要告诉用户缺什么、冲突在哪里、能不能修。

第五个坑是“AI 味”。如果 Prompt 写得太泛，生成的笔记会很漂亮，但没有信息量。哔知的笔记应该更像骨架版知识卡：工具名、项目地址、解决的问题、适用场景、限制风险、下一步行动，而不是一篇通顺的观后感。这个方向还需要继续打磨，但我已经越来越确定，少而准比长而全更有价值。
