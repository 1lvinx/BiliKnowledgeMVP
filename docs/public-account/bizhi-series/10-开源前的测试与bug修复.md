# 开源前的测试与 bug 修复

**文 / 逸峰AI**

哔知做到 Beta 后，我越来越清楚一件事：开源前最重要的工作，不是继续加新功能，而是把真实链路跑稳。一个项目如果只在 Demo 数据里表现正常，放到用户自己的收藏夹、字幕、模型环境和系统依赖里，很快就会暴露问题。开源意味着别人会用完全不同的机器、网络、账号和习惯来测试它，这时每一个小 bug 都会变成真实阻塞。

我现在最关注的是 P0 链路：收藏夹导入、字幕获取、本地转写、洞察生成、笔记生成、开源项目提取、知识库验证。每一步都要能单独运行，也要能串起来跑。如果字幕缺失，应该提示用户抓字幕或本地转写；如果 ASR 低置信，应该允许继续但提醒人工抽查；如果 AI API 没配置，要明确告诉用户缺什么，而不是只抛出一段后端错误。用户不需要知道底层实现有多复杂，但需要知道下一步怎么处理。

这段时间修得最多的，是那些看似不大的体验问题。比如模型进度条被当成错误输出，导致用户以为转写失败；本地转写成功后，洞察脚本仍按旧规则判断字幕不可用；笔记生成后没有正确回到笔记列表；处理中心里状态提示太多，反而看不出主次。这些问题单个看都不致命，但连在一起就会让人失去信心，所以必须在开源前解决。

测试也不能只靠自动化。自动化测试能检查配置校验、路径安全、状态文件和知识库结构，但真正的产品测试还要用真实视频。我的标准很简单：15 秒到 30 分钟的视频，能稳定完成字幕、洞察和笔记；每天处理 5 到 10 条，不追求批量跑满收藏夹；失败时要能解释原因，并尽量给出修复路径。这个标准不夸张，但足够贴近日常使用。

开源前还要准备一套问题处理机制，包括 Doctor 诊断、FAQ、Issue 模板、示例数据和日志说明。用户遇到问题时，最好能先通过 Doctor 自查依赖、Cookie、模型和 API；如果仍然解决不了，再把日志、BV 号、操作步骤和截图提交给作者。这样反馈才有上下文，维护也不会陷入猜谜。

我希望哔知开源时不是一个“功能很多但到处漏水”的项目，而是一个边界清楚、链路稳定、问题可定位的工具。它可以不完美，但不能让用户不知道为什么失败。开源前的测试和 bug 修复，就是把这些不确定性尽量提前消化掉，让第一次使用的人能顺利走完最核心的一条路。
