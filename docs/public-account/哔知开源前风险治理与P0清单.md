# 哔知开源前风险治理与 P0 清单

**文 / 逸峰AI**

这段时间，哔知已经从一个产品想法，逐渐进入 Beta Candidate 阶段。

核心链路已经跑通：

```text
B站收藏夹
→ 选择视频
→ 抓取字幕 / 本地转写
→ 生成视频洞察
→ 生成精炼笔记
→ 识别 GitHub 开源项目
→ 沉淀到个人知识库
```

但如果哔知后续准备开源，就不能只从“功能是否可用”的角度看问题。

更重要的是，要提前思考：

```text
开源后用户会怎么用？
哪些地方最容易误解？
哪些风险必须提前写清楚？
哪些能力必须在开源前补齐？
```

这份文档，就是哔知开源前的风险治理清单。

---

## 一、哔知不能定位成“全自动总结器”

这是最重要的产品边界。

哔知不应该被定义为：

```text
自动总结所有视频的 AI 工具
```

而应该被定义为：

```text
半自动视频知识工作台
```

也就是说：

- 用户负责选择真正值得沉淀的视频；
- AI 负责字幕整理、洞察提取、笔记结构化、项目线索识别；
- 用户最终负责判断、标签、取舍和复用。

这条边界非常关键。

因为如果把哔知包装成“全自动总结器”，用户就会天然期待：

```text
导入全部收藏夹
一键总结所有视频
自动生成完整知识库
```

但这不是当前阶段最合理的方向。

真正有价值的知识沉淀，不是批量制造内容，而是精选、判断和复用。

所以哔知更适合承诺：

```text
我帮你把真正值得留下的视频，整理成可复用的知识资产。
```

而不是承诺：

```text
我帮你自动总结所有视频。
```

---

## 二、必须限制批量处理预期

开源后，很多用户天然会问：

```text
能不能一次处理 5000 个收藏视频？
```

这个问题必须提前回答。

建议明确写在 README 和使用文档里：

```text
不建议批量处理大量视频。
```

推荐使用方式应该是：

```text
每天精选 5 - 10 条真正值得沉淀的视频。
优先处理短视频到 30 分钟左右的中等长度视频。
不建议高并发抓取。
不建议把哔知当成爬虫工具。
```

这样做有几个原因。

第一，保护用户账号。

如果大量抓取 B 站内容，可能触发平台风控、限流或登录态失效。

第二，保护本地体验。

字幕抓取、本地转写、AI 调用、文件写入都会消耗资源。

如果后台高并发运行，很容易导致 App 卡顿、任务失败、结果不稳定。

第三，保护知识质量。

批量生成几千条笔记，不等于拥有几千条知识。

更可能只是把视频收藏夹，变成另一个 AI 笔记垃圾堆。

哔知应该从流程上鼓励用户做筛选。

先判断视频是否值得沉淀，再触发生成。

## 三、Doctor 必须成为开源前核心功能

哔知不是一个纯前端工具。

它依赖本地环境和多个外部能力：

- Python；
- ffmpeg；
- yt-dlp；
- ASR 依赖；
- 模型缓存；
- AI API；
- B站登录态；
- 本地知识库目录。

所以 Doctor 诊断不是锦上添花。

它是开源前的基础设施。

Doctor 至少应该能检测：

```text
Python 路径
ffmpeg 是否可用
yt-dlp 是否可用
ASR 依赖是否完整
模型是否存在
B站登录状态是否有效
AI API 是否配置
知识库目录是否健康
```

更进一步，Doctor 应该能做到：

```text
发现问题
解释问题
给出修复建议
尝试自动修复
修复后重新检测
```

比如：

- 检测不到 ffmpeg，就提示安装方式；
- Python 环境不对，就提示当前路径和推荐路径；
- ASR 包缺失，就提示缺少哪些依赖；
- 模型缓存不存在，就提示需要下载；
- B站登录态失效，就提示重新登录；
- AI API 未配置，就提示无法生成洞察和笔记。

如果没有 Doctor，开源后大量 Issue 很可能会集中在：

```text
为什么抓不到字幕？
为什么本地转写失败？
为什么生成笔记失败？
为什么我的环境能跑，你的文档跑不起来？
```

Doctor 的目标，就是把这些问题尽量前置、自动化和可解释化。

## 四、B站合规和风控必须提前写清楚

哔知强依赖 B 站内容。

这意味着开源后必须明确合规边界。

README 里建议提前声明：

```text
哔知仅用于个人知识整理。
不建议批量抓取。
不提供绕过平台限制能力。
用户需自行遵守 B站相关规则。
请勿将抓取内容用于商用、公开分发或侵犯版权的用途。
```

这是非常关键的一段。

因为用户可能会误解哔知的用途，把它当成批量抓取工具。

这不仅会增加账号风险，也会给项目带来不必要的合规压力。

另外，还需要提供兜底方案：

```text
如果无法抓取字幕，可手动导入字幕，或使用本地转写。
```

这样即使 B 站接口变化、登录态失效、字幕不可用，用户也有备用路径。

## 五、AI 成本必须提示

如果用户使用云端大模型生成洞察和笔记，就会产生 API 成本。

这件事必须提前说明。

尤其是长视频。

如果用户导入几个小时的视频字幕，一次请求可能消耗大量 token。

所以哔知需要考虑：

- 字幕长度提示；
- token 成本预估；
- 超长字幕截断；
- 分段处理策略；
- 用户确认机制；
- 默认限制最大处理长度。

README 中也应该写清楚：

```text
AI API 调用可能产生费用，请按需使用。
建议优先处理高价值视频，避免批量生成造成不必要成本。
```

这不仅是技术问题，也是用户信任问题。

---

## 六、总结质量不能过度承诺

AI 生成的洞察和笔记，质量受很多因素影响：

- 字幕是否完整；
- 字幕是否准确；
- 视频内容是否有信息密度；
- 是否存在大量口水话；
- Prompt 是否适配；
- 模型能力是否足够；
- 用户选择的视频是否真的适合沉淀。

所以不能对外承诺：

```text
所有视频都能生成高质量笔记。
```

更合理的说法是：

```text
哔知更适合处理信息密度较高、具有学习或研究价值的视频。
对于娱乐、剧情、综艺、闲聊类视频，生成效果可能有限。
```

这个边界要提前说明。

否则用户拿番剧、综艺、纯娱乐视频去测试，然后说“这个工具不好用”，其实是使用场景不匹配。

## 七、内容版权和使用边界

哔知用于个人知识整理。

但如果有人用它批量抓取 UP 主视频内容，并公开分发字幕、笔记或整理稿，就可能引发版权问题。

所以开源文档里需要加入免责声明：

```text
本项目仅用于个人学习、研究和知识管理。
请勿批量抓取、公开分发、商业化使用未经授权的视频内容、字幕或衍生笔记。
用户应自行承担使用本工具带来的平台规则和版权风险。
```

这不是为了吓退用户。

而是明确项目边界。

## 八、模块解耦是长期维护的关键

如果哔知后续开源，长期维护压力一定会出现。

尤其是：

- B站接口变化；
- 字幕抓取失败；
- AI 模型切换；
- ASR 依赖更新；
- 前端交互变更；
- 笔记模板迭代。

所以架构上不能把所有逻辑绑死。

建议尽早解耦为几个模块：

```text
B站解析模块
字幕获取模块
ASR 本地转写模块
AI 洞察生成模块
笔记生成模块
开源项目识别模块
知识库索引模块
Doctor 诊断模块
```

这样未来即使某一块失效，也可以局部替换。

社区贡献者也更容易参与。

比如有人只维护 B站解析，有人只优化 Prompt，有人只改 ASR，有人只做 UI。

这会降低作者本人的长期维护压力。

## 九、开源前 P0 风险清单

下面是哔知开源前建议优先完成的 P0 清单。

```text
P0-1 Doctor 诊断和修复
P0-2 README 安装说明
P0-3 隐私与免责声明
P0-4 使用频率建议
P0-5 手动字幕导入兜底
P0-6 AI 成本提示 / 字幕长度截断
P0-7 Issue 模板
P0-8 示例数据清理
P0-9 B站 Cookie 失效提示
P0-10 模块解耦：B站解析 / ASR / AI / 笔记生成
```

### P0-1 Doctor 诊断和修复

确保新用户能快速知道自己缺什么依赖、哪里配置错了、下一步怎么修。

### P0-2 README 安装说明

清楚说明项目定位、安装步骤、依赖、运行方式和限制。

### P0-3 隐私与免责声明

说明数据存储位置、AI API 调用边界、B站内容使用边界和用户责任。

### P0-4 使用频率建议

明确不建议批量抓取，不建议高并发，推荐每天精选少量视频。

### P0-5 手动字幕导入兜底

当字幕接口不可用、本地转写失败时，允许用户手动导入字幕继续生成洞察和笔记。

### P0-6 AI 成本提示 / 字幕长度截断

避免用户无意识处理超长视频，导致 API 成本过高。

### P0-7 Issue 模板

让用户反馈问题时提供必要信息：系统版本、Doctor 日志、视频 BV 号、操作步骤、错误截图。

### P0-8 示例数据清理

开源仓库不能包含个人收藏夹、Cookie、API Key、真实笔记等敏感数据。

### P0-9 B站 Cookie 失效提示

登录态失效时，应明确提示重新登录，而不是只显示抓取失败。

### P0-10 模块解耦

把 B站解析、ASR、AI、笔记生成等模块拆开，方便维护和社区贡献。

## 十一、最终定位

哔知最稳的定位不是：

```text
自动总结所有视频。
```

而是：

```text
帮你把真正值得留下的视频，整理成可复用的知识资产。
```

这句话应该贯穿 README、公众号文章和产品介绍。

它能自然区分哔知和普通 AI 总结工具。

也能避免用户对“全自动批量总结”产生错误期待。

真正能长期活下来的知识工具，不应该鼓励用户囤积更多信息。

而应该帮助用户留下更少、更准、更有价值的知识。
